# Safety Sensor 与相机 192.168.5.100 通讯延时测试报告

> 测试日期：2026-09-10
> 测试主机：Linux Ubuntu 22.04 / Python 3.10.12
> 目标相机：`192.168.5.100:8000`（PM Camera，平台信封 `{code,data,error_message,metrics.api_ms}`）
> 测试脚本：[`bench_camera.py`](../bench_camera.py)（新增）、[`test_alarm_receiver.py`](../test_alarm_receiver.py)、[`bench_alarm.py`](../bench_alarm.py)

---

## 1. 摘要（TL;DR）

| 指标 | 结论 |
|---|---|
| **网络层 RTT（ICMP ping）** | avg **2.90 ms**，链路健康、0 丢包 |
| **TCP 三次握手** | avg **2.86 ms**，与 ping 一致 |
| **HTTP PATCH `/gpio/do/1` 串行 RTT** | avg **24.11 ms**，p95 32.68 ms |
| **↳ 其中相机服务端处理（api_ms）** | avg **9.03 ms** |
| **↳ 网络 + HTTP 栈开销** | ≈ 15 ms |
| **HTTP PATCH 10 并发吞吐** | **25.7 req/s**（相机侧瓶颈） |
| **本地接收服务基线（bench_alarm.py）** | 串行推送 avg 3.04 ms、并发吞吐 153.6 req/s |
| **鉴权状态** | 默认 `camera-token` 被相机拒绝（401「无效的令牌」），当前测得为**鉴权短路分支**延时 |

**核心结论**：本机 → 相机的**单次反控联动往返约 24 ms**，网络本身只占 ~3 ms，主要开销在相机 HTTP 栈与业务处理。相机 HTTP 服务并发能力弱（10 并发即跌至 25.7 req/s），生产环境需**避免对同一相机高频触发 DO 联动**。

## 2. 测试背景

现有测试脚本 [`test_alarm_receiver.py`](../test_alarm_receiver.py) 与 [`bench_alarm.py`](../bench_alarm.py) 按 [TEST.md](../TEST.md) 所述**仅测试本地 127.0.0.1 的接收服务**（临时端口 8123 / 8124），**不涉及任何外部相机通讯**。为量化 [`alarm_receiver.py`](../alarm_receiver.py) 中 `trigger_linkage()` → `_camera_patch()` 反控联动链路的真实延时，本次新增 [`bench_camera.py`](../bench_camera.py) 直接对相机施压。

## 4. 测试方法

### 4.1 分层测量口径

| 层次 | 手段 | 反映内容 |
|---|---|---|
| L3 网络层 | `ping -c 20 -i 0.2` | 纯 IP 往返，不含 TCP/HTTP |
| L4 传输层 | `socket.create_connection` × 50 | TCP 三次握手 ≈ 1×RTT + 内核调度 |
| L7 应用层（基线） | `HTTP GET /` × 100 | 完整 HTTP 请求（相机返回 404 信封） |
| L7 应用层（业务） | `HTTP PATCH /gpio/do/1` × 100（串行） | 反控联动实际调用 |
| L7 应用层（并发） | `HTTP PATCH /gpio/do/1` × 100 / 10 线程 | 并发吞吐与延时分布 |

### 4.2 统计项

`min / avg / p50 / p95 / max`（毫秒）；若响应含 `metrics.api_ms`，额外输出**服务端处理耗时均值**，用以拆分「网络 + HTTP 栈」与「相机业务逻辑」两部分。

## 6. 结果分析

### 6.1 延时构成拆分（PATCH /gpio/do/1 串行）

```
总 RTT 24.11 ms
├── 网络层 RTT          ~2.90 ms   (12%)   ← ping 实测
├── TCP 建连 + HTTP 栈  ~12.18 ms  (51%)   ← 24.11 - 2.90 - 9.03
└── 相机服务端 api_ms    ~9.03 ms   (37%)   ← 相机自报
```

- **网络本身不是瓶颈**：ping avg 2.90 ms 表明二层链路健康
- **HTTP 栈开销偏大**（~12 ms）：`urllib.request` 每次新建连接、无 Keep-Alive；相机侧 nginx/上游服务握手 + Header 解析亦占时
- **相机业务处理 9 ms**：当前是 401 鉴权短路分支，**真实成功路径（GPIO 置位）会更慢**，需拿到有效 Token 后复测

### 6.2 毛刺来源

| 现象 | 归因 |
|---|---|
| HTTP GET / max=731.53 ms | 单次冷启动或相机侧 GC / 调度抖动；同期 api_ms 均值仅 4.62 ms，非业务耗时 |
| PATCH 10 并发 avg 从 24 → 387 ms（16×恶化） | 相机 HTTP 服务并发能力弱，api_ms 从 9 → 230 ms 说明**相机侧串行处理请求** |
| ping p95=7.47 ms 而 min=1.47 ms | 无线/交换机队列偶发抖动，属可接受范围 |

### 6.3 与本地服务对比

| 维度 | 本地 alarm_receiver | 相机 API |
|---|---|---|
| 串行 avg RTT | 3.04 ms | 24.11 ms（**8× 慢**） |
| 服务端 api_ms | 1.44 ms | 9.03 ms（**6× 慢**） |
| 10 并发吞吐 | 153.6 req/s | 25.7 req/s（**6× 低**） |
| 10 并发 avg RTT | 60.97 ms | 386.89 ms（**6× 慢**） |

**本机 `alarm_receiver` 不是瓶颈，相机 HTTP 服务才是瓶颈**。

### 6.4 与 [TEST.md](../TEST.md) 基线对比

TEST.md 中 Windows 环境基线：串行推送 avg 7.00 ms、并发吞吐 176.7 req/s。
本次 Linux 环境实测：串行推送 avg 3.04 ms、并发吞吐 153.6 req/s。
**均满足 TEST.md 第 5 节验收基线（串行 avg < 20 ms、并发吞吐 > 100 req/s）**。

## 7. 遗留问题与建议

### 7.1 阻塞项

| # | 问题 | 影响 | 处理建议 |
|---|---|---|---|
| 1 | `CAMERA_TOKEN = "camera-token"` 被相机拒绝（401） | 无法测得反控联动**成功路径**的真实延时 | 向相机管理员获取有效 Token，重跑 `python3 bench_camera.py --token <真实Token>` |
| 2 | `alarm_receiver.py` 中 `CAMERA_BASE_URL = ""`（空） | **联动逻辑当前不会触发** | 修改为 `CAMERA_BASE_URL = "http://192.168.5.100:8000"` |

### 7.2 优化建议

| # | 建议 | 理由 |
|---|---|---|
| 1 | **联动去重锁**：同一相机 DO 通道在 `DO_HOLD_SECONDS` 内正在持有时，跳过新的联动请求 | 相机 10 并发吞吐仅 25.7 req/s，`trigger_linkage()` 每条 level≥3 报警起一个线程，高频报警会堆积 |
| 2 | **HTTP Keep-Alive**：`_camera_patch()` 目前每次新建连接，可改用 `http.client.HTTPConnection` 复用 | 消除 ~12 ms 的 TCP 建连 + HTTP 栈开销中的重复部分 |
| 3 | **超时降级**：`urlopen(req, timeout=5)` 遇相机阻塞时会挂 5s，建议缩短到 1~2 s 并加告警 | 相机并发时 max RTT 达 1011 ms，接近超时边界 |
| 4 | **联动失败重试策略**：目前 `_camera_patch` 失败仅打印，建议加 1~2 次指数退避重试 | 单次毛刺（GET max 731 ms）可能吞掉一次联动 |
| 5 | **验收基线补充**：TEST.md 目前只有本地基线，建议追加「相机联动串行 avg < 50 ms、并发吞吐 > 20 req/s」作为验收项 | 覆盖真实链路 |

### 7.3 复测指引

```bash
# 1. 拿到真实 Token 后重跑（关键）
python3 bench_camera.py --token <真实Token> --n 200

# 2. 长时间稳定性测试（观察是否有周期性毛刺）
python3 bench_camera.py --n 1000 --concurrency 1

# 3. 端到端联动验证（需先修改 alarm_receiver.py 的 CAMERA_BASE_URL 与 CAMERA_TOKEN）
python3 alarm_receiver.py 8000 &
curl -X POST http://127.0.0.1:8000/api/v1/alarms \
     -H "Authorization: Bearer safety-sensor-token" \
     -H "Content-Type: application/json" \
     -d '{"alarm_no":"E2E-001","camera_id":"cam-1","level":3,"title":"端到端联动测试"}'
# 观察 alarm_receiver 日志是否出现 [linkage] DO1 -> 1 / -> 0
```

### 8.3 术语

| 术语 | 定义 |
|---|---|
| RTT | Round-Trip Time，客户端从发起请求到读完响应的 wall-clock 时间 |
| api_ms | 相机响应信封 `metrics.api_ms` 字段，仅服务端处理耗时 |
| p50 / p95 | 分位数延时，50% / 95% 的请求快于该值 |
| DO | Digital Output，相机 GPIO 数字输出通道 |
| 反控联动 | 报警级别 ≥ `LINKAGE_LEVEL` 时，`alarm_receiver` 主动 `PATCH` 相机 DO 置高，`DO_HOLD_SECONDS` 后复位 |
